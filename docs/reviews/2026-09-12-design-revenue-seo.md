**645.live 디자인·광고 수익·문구·SEO 개편 검토**

검토일: 2026-09-12. 현재 수익이 발생 중인 서비스를 개선한다는 전제로 작성했다. 저장소와 공개 운영 화면을 확인했고, 사이트맵 173개 URL 및 추가 15개 URL의 응답 HTML을 점검했다. 아래는 구현 전 기준선과 제안이다. 이후 진행한 구현·검증·운영 설정은 [구현 기록](2026-09-12-redesign-implementation.md)을 참고한다. 광고 계정의 수익 지표와 설정은 직접 확인하지 않았다.

추천 방향은 **모바일에서 당첨 결과와 확인 도구를 먼저 제공하고, 통계·회차 해설·당첨점 탐색이 자연스럽게 이어지는 로또 정보 서비스**다. 기존 데이터와 기능을 활용하면서 공통 레이아웃, 정보 우선순위, 광고 위치, 문구를 함께 다시 설계한다. 수익 목표는 방문자당 광고 수익과 재방문을 함께 높이는 것이다.

**운영 화면에서 확인한 문제**

화면 수치는 브라우저 390×844 CSS px에서 관찰한 한 시점의 값이다. 광고 삽입 시점과 환경에 따라 달라질 수 있으며, 실제 사용자 성능 지표나 전체 방문자 행동을 의미하지 않는다.

**디자인과 화면 구성안**

시각 방향은 밝은 중립 배경, 짙은 본문색, 블루 한 가지 강조색, 정돈된 숫자와 표다. 로또 번호 구간의 다섯 색은 데이터 표식에만 사용한다. 큰 그림자와 장식 그라데이션을 줄이고, 구획·여백·타이포그래피로 중요도를 표현한다.

홈의 권장 순서는 `발표 완료 결과 → QR 확인·번호 만들기 → 첫 광고 → 스캔 요약 → 통계·회차 해설 → 관련 탐색`이다. 광고가 첫 방문자의 핵심 정보 확인을 밀어내지 않도록 한다. 추첨 대기·반영 중·반영 완료·데이터 오류 상태를 별도로 설계한다.

| 번호 생성 | 기본 조건·생성 버튼·생성 결과 | 고급 조건·결과 복사·관련 통계 | 반복 클릭 영역 제외, 결과 이후 내용 영역 |

위 슬롯 수는 실험을 시작하기 위한 제안이며 최적 수량이나 Google의 고정 제한을 의미하지 않는다. 당첨점의 지역 필터, 생성 결과 복사 등 현재 없는 기능은 별도 구현 항목으로 관리한다.

**수익 개선 방법**

현재 코드에는 공통 AdSense 스크립트가 있고, 검색 범위에서 명시적인 `data-ad-slot`·`adsbygoogle.push` 기반 수동 광고 컴포넌트는 발견하지 못했다. 뉴스 피드의 삽입 구조는 존재하지만 서버가 `feedInsertions: []`를 내려준다. 실제 운영에서는 자동 광고가 관찰됐다. 계정의 형식별 수익·광고 로드·자동 실험 설정은 이번 검토에서 확인하지 않았다.

첫 개편에서는 `AdSlot`과 페이지 유형별 설정을 도입해 광고 위치, 슬롯명, 크기 예약, 중복 초기화 방지, 개발 환경 비활성화, 광고 미노출 상태를 관리하는 것이 좋다. 자동 광고와 수동 광고를 함께 사용할 때는 합산 밀도를 확인한다. 자동 광고의 제외 영역은 본문 광고에 적용되며 앵커 같은 오버레이를 막지는 않는다. 앵커·광고 의도 링크·칩은 각 형식 설정에서 별도로 검토해야 한다. [Google 자동 광고 설정](https://support.google.com/adsense/answer/9305577?hl=en), [제외 영역 범위](https://support.google.com/adsense/answer/12626543?hl=en).

광고의 실제 가시성이 중요하다. 일반 디스플레이 광고의 Active View 기준은 50% 이상이 연속 1초 보이는 것이다. 페이지가 길다고 유효 노출이 늘어나는 것은 아니므로, 사용자가 읽거나 결과를 확인하는 지점에 맞춰 배치한다. 광고의 시각적 구분, 조작 버튼과의 분리, 자동 새로고침 방지도 설계에 포함한다. [Google 가시성 가이드](https://support.google.com/adsense/answer/6219980?hl=en), [광고 배치 정책](https://support.google.com/adsense/answer/1346295?hl=en).

| 측정 항목 | 쓰임 |
| --- | --- |
| 수익 ÷ 방문자 또는 세션 × 1,000 | 체류·페이지 탐색을 포함한 사업 성과. 각 데이터의 집계 정의·기간·시간대를 맞춤 |
| Page RPM, 총수익 | 페이지 효율과 전체 수익을 함께 확인 |
| 광고 노출·채움·Active View | 광고가 실제로 제공되고 읽는 위치에 보이는지 확인 |
| QR 확인 완료율·번호 생성 완료율 | 수익 실험이 핵심 작업을 방해하는지 확인 |
| 다음 페이지 이동률·7일 재방문 | 유용한 탐색과 반복 방문 확인 |
| 페이지 유형별 LCP·INP·CLS | 광고와 화면 변경의 속도·반응·안정성 영향 확인 |

단순 설명용 관계식은 `수익 ≈ 페이지뷰 × Page RPM ÷ 1,000`이다. Page RPM에는 광고 노출·가시성·경매 조건 등이 이미 반영되므로 여기에 가시성 비율을 다시 곱하지 않는다. 실제 수익과 트래픽 정보가 없어 수익 증가율은 예측하지 않았다.

기준선은 최근 28일의 요일·기기·랜딩 페이지·광고 형식별 지표로 잡는다. 이후 한 번에 한 가설을 검증한다. 예를 들어 ‘홈 결과 우선 구성’, ‘본문 광고 의도 칩 사용 여부’, ‘앵커 위치·형식’, ‘기사 첫 광고 위치’를 구분한다. 최소 2–4회의 주간 추첨 주기를 포함하되 트래픽과 변동성에 따라 충분한 표본을 확보한다. 디자인 효과와 광고 설정 효과를 같은 실험으로 섞지 않는다. Google의 자동 광고 실험은 사이트당 한 개만 동시 실행할 수 있고 페이지 제외는 실험 대상이 아니다. [AdSense 실험](https://support.google.com/adsense/answer/9726342?hl=en).

**문구 개편 원칙과 예시**

화면은 ‘무엇을 확인하고 무엇을 누르면 되는지’를 먼저 말한다. 검색 제목·설명은 페이지 주제와 범위를 구체적으로 설명한다. 동일한 긴 문장을 화면 제목·카드·메타에 반복 사용하지 않는다.

| 현재 문구 | 제안 | 이유 |

**길이 외의 SEO 개선 항목**

1. **기간별 통계 제목 중복.** `/stats/high-low/recent/*`, `/stats/sections/recent/*`, `/stats/repeat/recent/*`, `/stats/unit-digit/recent/*`는 10·20·50·100회 페이지가 각각 같은 제목이다. 제목과 H1·설명에 기간을 일치시킨다. 중복 제목이 반드시 색인 실패를 뜻하지는 않지만 검색 결과에서 구분이 어렵다.
2. **예측 표현 정리.** AC·색상 통계 일부 메타와 번호 상세의 ‘궁합’ 등은 과거 데이터 설명으로 교체한다. 문자 수가 충분해도 제공 가치가 부정확하면 좋은 설명이 아니다.
3. **번호 URL의 HTTP 상태.** `/n/46`, `/stats/numbers/46`은 실제 500 응답. 전자는 404 예외를 catch에서 500으로 덮고, 후자는 일반 Error를 던진다. 잘못된 번호는 일관된 404와 복귀 동선을 제공하고 서버 장애와 구분한다.
4. **사이트맵 갱신 신호.** 기본 `/sitemap.xml`의 `/stats` lastmod는 2026-03-30, 실제 통계 갱신은 2026-09-12. 별도 `/stats-sitemap.xml`은 최신 데이터 시각을 제공하지만 robots에는 기본 사이트맵만 선언돼 있다. 계정에 별도 제출했는지는 미확인이다. 사이트맵 인덱스 또는 robots 선언으로 발견 경로를 통합하고, 코드 파일 mtime 대신 유의미한 데이터·콘텐츠 변경 시각을 적용한다. 변하지 않은 가이드에 매일 최신 통계 시각을 붙이는 것도 피한다.
5. **회차 canonical은 제품 의도에 맞춰 결정.** `/history?round=1240`은 `/history`로 canonical을 통합하고 제목·설명도 같다. 탐색용 필터라면 가능한 정책이다. 회차별 검색 유입을 원한다면 고유 결과 콘텐츠·URL·메타·내부 링크를 갖춘 별도 랜딩 구조를 설계해야 한다. 개편에서 무작정 canonical만 바꾸지 않는다.
6. **번호 페이지 역할 중복.** `/n/{번호}`와 `/stats/numbers/{번호}`는 각 45개 URL이다. 전자는 스캔 현황, 후자는 공식 추첨 통계라는 차이를 제목·상단·메타에 명확히 반영한다. 통합할 경우 기존 유입과 링크를 확인해 301 매핑을 마련한다.
7. **페이지별 공유 정보.** `/news` 등 일부 공개 페이지는 OG 이미지가 없다. 검색 색인의 필수 조건은 아니지만 공유 품질을 위해 공통 기본 이미지와 고유 제목·설명을 적용한다.
8. **상태 페이지의 제목 계층.** `/status`에는 H1 두 개가 있다. 페이지 제목과 정상 상태 메시지의 역할을 나눈다. H1 개수만으로 순위 문제가 확정되는 것은 아니다.
9. **에이전트 화면.** `/?mode=agent`는 별도 canonical·영문 제목·홈과 동일한 한글 설명을 갖고 indexable이다. 검색 노출 목적을 정해 고유 메타·언어 설정을 적용하거나 검색 대상에서 제외한다. 일반 사용자 메인 문구와는 분리한다.
10. **구조화 데이터.** 현재 JSON-LD는 파싱되지만 본문·숫자·출처·수정 시각과의 일치 검증이 별도로 필요하다. FAQ 마크업이 있다고 검색 노출 기능이 보장되지는 않는다. 키워드나 스키마 유형을 늘리는 것보다 본문 정확성과 정보 접근성을 우선한다.

토큰은 `app.css`에서 제품 의미에 맞게 정의하고 기존 daisyUI를 점진적으로 연결한다. `--b1`, `--bc`, `--p` 같은 구형 토큰 참조가 통계와 모바일 CSS에 남아 있다. 운영 페이지에서 `--b1`은 빈 값, `--color-base-100`은 정의된 값으로 확인했으므로 실제 색·포커스 적용을 점검하고 v5 토큰으로 통합해야 한다. 공 컴포넌트도 `SimpleBall`, 통계용 `LottoBall`, 실시간용 `LottoBall`의 표현을 공통화한다.

QR 화면 1,336줄, 통계 허브 903줄, 생성기 761줄로 UI·상태·로직이 큰 파일에 모여 있다. 디자인 교체 지점에서 카메라·처리 결과·조건 입력·통계 요약·광고를 분리하되, 검증된 동작을 한 번에 다시 작성하지 않는다. 전역 실시간 연결과 Clarity 초기화가 직렬로 묶여 있는 부분, 생성기가 통계 요청 6개 완료를 기다리는 부분은 핵심 작업의 의존성을 줄일 후보다. 성능 저하 정도는 별도 실측이 필요하다.

현재 `bun run www check`는 **0 errors / 0 warnings**로 통과했다. Svelte 분석기에서도 공통 레이아웃의 직접적인 issue는 없었다. 이는 광고 중첩·모바일 가독성·실기기 카메라 품질·검색 노출을 보증하지 않는다. 개편 검증에는 대표 사용자 흐름과 실제 광고가 켜진 화면을 포함해야 한다.

성능 기준은 실제 사용자 p75에서 LCP ≤2.5초, INP ≤200ms, CLS ≤0.1을 목표로 삼는다. 광고 공간을 미리 예약하고 미채움·오류 때도 갑작스러운 레이아웃 이동을 피한다. 이번 검토에서는 Lighthouse 점수나 실제 사용자 CWV를 측정하지 않았다. [Web Vitals 기준](https://web.dev/articles/vitals).

미확인 사항은 AdSense 형식별 수익·RPM·실험 설정, GA4의 모바일 비중·행동 전환, Bing의 정확한 경고 URL·수집일·색인 현황이다. 따라서 제안 슬롯과 화면 우선순위는 검증할 가설이며 수익 상승을 확정한 결과가 아니다.
